# 2026.11.13b2

Opt-in sign-in and arming test for [#157](https://github.com/ibasebcast/ha-alarmdotcom/issues/157), on top of 2026.11.13b1.

- Report a declined panel command (Alarm.com status 422) as a declined command instead of a wrong verification code. The message says whether the system needs its issues acknowledged or is not ready to arm, when Alarm.com's reply or the panel's own status shows it. Alarm.com's error text is not copied into the message or the logs, because it can name zones, devices or the account.
- When Alarm.com declines an arm request that used Force Bypass, retry once without Force Bypass. The original integration intended this retry, but it never ran.
- Give the account identity lookup 90 seconds in total across both attempts (was 30 seconds per attempt). The first attempt is capped at 60 seconds so a retry still fits. The session repair and entry load limits are raised to fit a full sign-in.

### What to test

In HACS, select this prerelease and restart Home Assistant. Keep your existing Alarm.com entry.

1. Check whether the entry loads on the first try. If it doesn't, share the new `Alarm.com setup could not connect` line.
2. When it is safe to do so, try **Arm Home** and **Arm Away** once each. If either fails, copy the new message exactly.

Please leave out account details, signed URLs, cookies, tokens and verification codes. Stable 2026.11.12 is available if you want to roll back.
